# 0단계 — 문제 정의와 재원 정리 (AI를 쓰기 전에)

> AI는 주어진 입력 안에서만 정확하다.
> 그래서 AI에게 일을 시키기 전에 **무엇이 문제인지**, **해결에 쓸 수 있는 재원이 무엇인지**를 먼저 정리했다.
> 이 문서가 이후 모든 단계의 입력이 된다.

## 1. 문제 상황
| 항목 | 내용 |
|---|---|
| 현재 방식 | 설계 쪽에서 받은 테스트벡터 RTL을 보며 SPI/I2C 장비용 시퀀스로 손으로 옮김 → 인가 → 결과를 눈으로 비교 |
| 문제 | IP·인터페이스가 바뀔 때마다 다시 옮겨 적음, 옮기는 실수(주소·비트·바이트 순서)가 그대로 시험 결과에 섞임 |
| 목표 | 테스트벡터 RTL을 넣으면 SPI / I2C 포맷 벡터가 자동으로 나오고, RTL 줄과 변환 줄을 거슬러 확인할 수 있는 툴 |
| 완료 기준 | ① 변환 결과가 프레임 형식과 일치 ② 변환 벡터를 칩(시연: DUT RTL)에 인가해 전 항목 PASS, 틀린 조건에선 FAIL ③ 다른 PC에서도 실행됨 |

## 2. 재원 (해결에 쓸 수 있는 것)
| 구분 | 재원 | 역할 |
|---|---|---|
| 입력 | 테스트벡터 RTL (<IP>/01_input/testvector/tv_*.v) | 변환 대상 |
| 입력 | 레지스터 정의 헤더 (*_regmap.vh) | 레지스터 기호 → 주소·폭 |
| 기준 문서 | 사양서 — 레지스터맵 (spec/ 4장) | 추출 결과를 대조할 기준 |
| 기준 문서 | 사양서 — SPI / I2C 프로토콜 (spec/ 3장) | 프레임 형식, 장치 주소, 모드, 비트 순서 |
| 업무 자산 | 시험 템플릿 (tool/config/test_template.yaml) | 팀에서 고정적으로 쓰는 시험 항목 구성 |
| 현장 지식 | "IP마다 엔디안이 다를 수 있다" | 사양서에 없는 정보 → AI가 알 수 없으므로 사람이 요구사항으로 추가 |
| 현장 지식 | "PC마다 Python 버전이 다르다" | 실행 환경 점검 기능 요구사항으로 추가 |
| 시험 대상 | 실물 칩 (시연: For Demo DUT RTL 시뮬레이션) | 변환 벡터가 맞는지 확인하는 곳 |
| 도구 | Python, Verilog 시뮬레이터, AI | AI는 구조화·코드 초안 담당 |

## 3. AI에게 맡길 것 / 내가 할 것
| AI | 사람 |
|---|---|
| 헤더 → 레지스터맵, 테스트벡터 파서, SPI/I2C 인코더 초안 | 사양서와 대조, IP별 수정, 변환 줄 대응 확인 |
| 정해진 규칙대로 코드 초안 작성 | 규칙(기대값 계산, 판정 기준) 자체를 정의 |
| 반복적인 형식 작업 | 현장 지식 반영, 최종 판단 |

## 4. 위험 요소 (미리 정한 확인 방법)
| 위험 | 확인 방법 |
|---|---|
| AI가 사양서 표를 잘못 읽음 | 레지스터마다 원문과 1:1 대조 |
| 사양서 자체가 실제 칩과 다름 (엔디안 등) | Chip ID처럼 값을 아는 레지스터를 읽어 교차 확인 |
| 판정 로직이 틀려서 FAIL을 못 잡음 | 일부러 틀린 조건으로 돌려서 FAIL이 나는지 확인 |
